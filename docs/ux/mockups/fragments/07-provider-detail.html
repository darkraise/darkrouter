Replace is two calls today: POST /api/providers/{id}/keys adds the new key, DELETE /api/providers/{id}/keys/{keyId} removes the old one. There is no replace route and no enable/disable route, so the switch above and this field both need the new PATCH. The field is write-only in both directions — what you type is encrypted at rest and never read back, and nothing in the API returns a secret in any form.

The three readouts report the credential-level entry, which is the one that makes the provider read as cooling in the list. The model triples above it cool and clear on their own ladders and are not derived from it.

Clears the four entries above and returns backoff_level to 0 without sending anything upstream. Today the only way to clear a cooldown from the console is to click Test and have it succeed, which means an operator who knows the key is fine still cannot say so — and an operator whose key is not fine gets no way to stop the ladder escalating.

Probe

55 · Probe — POST /api/providers/{id}/test {ok,probe,latency_ms,model_count,error}. Bypasses the breaker by design; a rejected key is a 200 with ok:false, not a 5xx.

One probe per provider at a time, 30s ceiling. It ignores the cooldown above on purpose: the usual reason to press it is to find out whether a cooling provider has recovered.

A successful probe resets the ladder for the credential it ran against — every triple and the credential-level entry — and triggers one discovery pass. That is the side effect region 4's Reset breaker button and region 6's Run discovery button exist to separate from it.

failed variant credential primary …a4f2 · ran 14:17:44

ok:false probelisting latency_ms1,204 errorthe provider rejected this credential: 401 Unauthorized

A rejected key is a 200 carrying ok:false, not a 5xx: the request to darkrouter succeeded and the answer is bad news. model_count is absent rather than 0 — nothing was listed, so there is no count to report. A failed probe clears nothing; the cooldown above stands.

Danger zone

77 · Delete — DELETE /api/providers/{id} returns dangling_aliases[]. A dangling alias is a warning, not a validation error.

Removes the provider, its three credentials and its breaker state. Requests already logged keep the id and stay readable; the catalog entries go with the next snapshot build.

Two aliases have a cerebras target in their chain and will lose it:

fast-coder alias chain, 1 target on cerebras cheap-embed alias chain, 1 target on cerebras

The delete still succeeds and reports them. That is deliberate: if a dangling alias were a validation error instead of a warning, this one click would make every subsequent config reload fail, and the operator would be left with a reload button that keeps failing and no way out of it but SSH.
