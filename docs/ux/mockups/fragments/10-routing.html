Resolution — first match wins

22 · Resolution — first match wins: alias, then provider/model (split on the FIRST slash, only when the prefix names a configured provider, so meta-llama/Llama-3.3-70B survives), then bare name in priority order.

1 exact alias name

The whole string is matched against the alias table exactly. A hit expands to that alias's ordered chain of targets and the walk stops here — rules 2 and 3 are never tried.

fast-coder → 8 targets

in the operator's order · no prefix match, no case folding, no trimming

2 provider/model

Split on the FIRST slash, and only when the prefix names a configured provider. Everything after that slash is the model id, slashes included, so a publisher path inside the model id survives.

openrouter/openai/gpt-oss-120b → openrouter + openai/gpt-oss-120b
meta-llama/Llama-3.3-70B → no split

meta-llama is not a configured provider, so the string survives intact and falls through to rule 3

3 bare model name

Expanded across every configured provider that offers the model, in provider priority order — one candidate per provider, credential and model, so a provider holding two keys contributes two candidates.

gemini-2.5-pro → vertex 100 › openrouter 70 › openrouter 70, key 2

nothing offers it → the request is rejected before any provider is called

Alias targets resolve one level only. A target that happens to name another alias is not followed. It is treated as a literal model string and handed to rules 2 and 3, which for an alias name almost always means it matches nothing at all and the chain simply carries on to the next target.

So vision holding a target fast-coder does not inherit fast-coder's eight candidates; it contributes zero, and the editor below flags it the same way it flags any other target that resolves to nothing.

Alias validation — cheap-embed

3-43-4 · Aliases — GET/PUT /api/aliases. New. Chains are yaml-only today and rendered as a JSON dump.

▵ This chain falls back across providers for one embedding model

text-embedding-3-large is served here by together and by deepinfra. Two providers hosting the same embedding model do not have to return the same vector: the scaling, and sometimes the normalisation, is the host's choice. A failover from together to deepinfra therefore writes vectors into the store that are not comparable with the ones already in it, and nothing downstream reports it — cosine similarity keeps returning a number either way.

This is a warning, not an error. The chain saves and routes; what it changes is what gets stored. If the vectors are persisted, pin the alias to one provider and let the request fail over to nothing rather than to a second scale. If they are compared only within one request, the fallback is safe.

Policy

55 · Policy — GET/PUT /api/policy. GET /api/config already returns the whole policy block and the SPA's Config type does not declare it.

retry

field value takes effect why
retry.max_attempts 4 hot-reloadable read per request while the ladder is walked — the next request sees it

cooldown

cooldown.trip_after 3 hot-reloadable consecutive failures before a provider is taken out of rotation
cooldown.max 15m hot-reloadable ceiling on the backoff a tripped breaker walks up · applies at the next trip

timeouts

timeout.connect 10s restart required a dialer field on the one shared HTTP transport, built once at startup
timeout.first_byte 60s restart required the same transport's response-header timeout, not a per-request value
timeout.total 10m hot-reloadable applied per request as a context deadline, read when the request starts
timeout.idle 120s hot-reloadable applied per request to the stream reader, between chunks

Two of the seven fields configure the single shared transport this process built when it started, so a reload writes them and nothing changes until the process is restarted. The other five are read per request and take effect on the next one. That difference is real today and the product does not say it anywhere, which is how an operator ends up convinced a timeout edit did not save.

Where this lives

66 · Storage — spec §8.1: imported once on first run, SQLite authoritative after. Same rule as providers:.

Aliases and policy are read out of darkrouter.yaml once, on first run, and live in SQLite from then on. After that import, editing aliases: or policy: in the file has no effect — exactly as editing providers: already has none. This screen writes the database; the file records how the database was first seeded.

darkrouter.yaml imported 2026-08-11 09:02 · 4 aliases, 7 policy fields · not read since
# Imported once, on first run. Edit these in configure/routing. # Changes made here are not read again. aliases: fast-coder: - groq/openai-gpt-oss-120b - cerebras/gpt-oss-120b - together/openai-gpt-oss-120b policy: retry: { max_attempts: 4 } timeout: { connect: 10s, first_byte: 60s, total: 10m, idle: 120s }

The alternative was an overlay where the file is the base and the database wins, which gives one value two sources of truth and no way to see which is in effect. So the import logs what it took, the file carries a comment block saying it will not be read again, and GET /api/config has to start distinguishing a value that came from the file from a value that is live — which today it cannot.
